# 手動測試優先順序清單（跨八份測試計畫）

> 這不是一份新的測試計畫，而是**既有八份計畫的索引與分層**。
> 案例的完整步驟與預期結果仍在原計畫裡，這裡只回答一件事：
> **「我現在該先測哪些？」**

## 為什麼需要這份清單

八份測試計畫累積了 **238 個未執行的案例**，全部平鋪、沒有優先順序。
照檔案順序跑，會先花一整天在「日常使用早就驗證過」的視覺迴歸上，
而真正會弄丟別人資料的案例排在最後。

## 分層

| 層級 | 數量 | 判準 | 什麼時候跑 |
|---|---|---|---|
| **P0** | **52** | 失敗會**弄丟別人的資料**或**讓人進不去** | 發給同學之前，全部 |
| **P1** | 26 | 自動測試只涵蓋一半，或中風險迴歸 | P0 之後，發布前最好跑完 |
| **P2** | 160 | 視覺細節，或日常使用已驗證 | 只在改到對應模組時回頭跑 |

> **2026-09-12 更新**：網域已設定完成，**52 個 P0 案例全部解鎖**。
> 先前卡住的 `otp_expired` 已查明是點到舊信／連結被消耗，流程本身正常。

## P0 — 擋住發布（52 個）

### P0-A　信件管道（6 個）✅ 網域已設定，可以跑了

來源：[2026-09-05-phase0-reliability.md](./2026-09-05-phase0-reliability.md) 案例 **1–6**

前置：照 [../auth-email-setup.md](../auth-email-setup.md) 走完七個步驟。
⚠️ 第 5 步（調高速率上限）與第 7 步（停用 Send Email Hook）最容易漏。

重點：用**不是你自己的** email 註冊收得到信、寄件人是你的網域、
**連續註冊 3 個帳號都收得到**（先前第 3 封被 2/hr 上限靜默擋掉）。

### P0-B　密碼重設走完整條（5 個）✅ 可以跑了

來源：[2026-09-05-phase0-reliability.md](./2026-09-05-phase0-reliability.md) 案例 **9、11、12、13、16**

重點：收信 → 點連結進入「設定新密碼」而非首頁 → 設定後**用新密碼真的能登入**。
Android（deep link `com.octofield.urniversity://`）與 Web 各走一次。

> 表單驗證與畫面路由已自動化（`test/widget/password_reset_test.dart`），
> 這五個測的是自動測試碰不到的部分：真實信件、真實 deep link、真實登入。
>
> ⚠️ **案例 12、13 要分成「同裝置」與「跨裝置」各走一次**。PKCE 把 code verifier
> 存在發出請求的那個裝置上，所以「手機按忘記密碼 → 筆電開信」會失敗並顯示
> 「請在按下『忘記密碼』的那個裝置與瀏覽器開啟連結」——那是預期行為，不是 bug。

### P0-C　訪客合併不遺失資料（7 個）✅ 現在就能跑

來源：[2026-09-05-phase0-reliability.md](./2026-09-05-phase0-reliability.md) 案例 **18–24**

**這是 Phase 0 最重要的一組。** 合併順序先前與外鍵順序完全相反，
每一筆有連結的資料都會遺失。

重點：訪客模式建立「願景 → 連結它的學期目標 → 連結該目標的任務」三層鏈，
登入選「整合進帳號」，**三筆全部要在，連結關係完整**。再測三層目標樹與子任務。
案例 20 的「重開 App 再看」是關鍵——證明真的寫進雲端。

### P0-D　列 id 不再碰撞（3 個）✅ 現在就能跑

來源：[2026-09-05-phase0-reliability.md](./2026-09-05-phase0-reliability.md) 案例 **25–27**

重點：**快速連續新增 5 個任務**，五個都要在，重開 App 後雲端也是五列。
先前同一毫秒建立的列會共用 id 互相覆蓋。

### P0-E　分類拖曳排序（6 個）✅ 現在就能跑

來源：[2026-08-23-known-issues.md](./2026-08-23-known-issues.md) 案例 **1–6**

`onReorder` → `onReorderItem` 遷移時的 off-by-one：舊 callback 傳原始索引，
新的已經預先調整過，呼叫端自己那行 `if (newIndex > oldIndex) newIndex--`
沒拿掉，**每一次往下拖都錯一格**。

重點：往下拖、拖到最後、拖到最前、相鄰對調，然後**重開 App** 確認順序真的存下來了。

### P0-F　清空回收桶（6 個）✅ 現在就能跑

來源：[2026-08-23-known-issues.md](./2026-08-23-known-issues.md) 案例 **7–12**

重點：案例 9 特別標了 ⚠️ ——清空後**在同一次開啟中**再刪一個任務，
看回收桶是否正常。案例 8 的「完全關掉 App 再開」驗證清空真的同步到雲端。

### P0-G　同步失敗的三個成因（19 個）✅ 現在就能跑

來源：[2026-08-25-sync-failures.md](./2026-08-25-sync-failures.md)

| 案例 | 內容 |
|---|---|
| 6、7 | `user_categories` 在 Dashboard 查 **不再是 0 列**（先前結構不相容，一列都沒寫進去過）；全 App 的分類顏色／圖示正確 |
| 9–12 | ⚠️ **關掉網路**改分類顏色 → **仍然要跳同步失敗**（用盡 3 次重試，約 1 秒），UI 不卡住；恢復網路後正常 |
| 14–20 | 回收桶還原的懸空外鍵：先還原**子**目標（不先還原父）→ 不跳失敗、子目標掛回頂層；重開 App 仍在 |
| 21–26 | 跨表連結：任務連結目標 → 先刪任務 → 再刪目標 → 還原任務 → 連結被清空、不跳失敗 |

## 建議的執行順序

```
P0（全部解鎖，52 個）
└─ P0-C  訪客合併        7 個   ← 最重要，測的是最嚴重的那個 bug
   P0-G  同步失敗       19 個
   P0-E  分類拖曳        6 個
   P0-F  清空回收桶      6 個
   P0-D  列 id 碰撞      3 個
   P0-A  信件管道        6 個
   P0-B  密碼重設        5 個   ← 含跨裝置那一次

發布前
└─ P1                   26 個
   P2 的 style 39、40     2 個（實機走查）
```

## 記錄結果

跑完之後，**把結果填回原計畫的表格**（「實際結果」與「通過？」兩欄），
不要填在這份索引裡。這份清單只負責排序，事實留在來源檔案。

發現新問題時，填進該計畫的「發現的問題」欄，並依
[../testing.md](../testing.md) §3 判斷是否需要開新的測試計畫。
